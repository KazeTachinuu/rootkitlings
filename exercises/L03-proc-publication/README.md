# L03: Publish a Read-Only Status File

L02 gave the module private state.
This exercise adds a small userspace view of the loaded module at
`/proc/rklings`.

While the module is loaded, reading that path returns `active`.
When the module unloads—or when publication fails—the path must not exist.

## What you will observe

```console
root@victim:~# insmod /rklings/rklings.ko
root@victim:~# cat /proc/rklings
active
root@victim:~# stat -c '%a' /proc/rklings
444
root@victim:~# rmmod rklings
root@victim:~# test ! -e /proc/rklings && echo absent
absent
```

The important behavior is the lifetime: the proc entry exists only while the
module owns every object needed to serve it.

## Understand a virtual file

`/proc` looks like a directory of files, but those files are generated by the
kernel when a process opens and reads them.
There is no `rklings` text file stored on disk.

```text
cat /proc/rklings
        | open and read
        v
procfs finds the registered entry
        |
        v
rk_status_show(output, unused)
        | seq_puts(output, "active\n")
        v
seq_file buffers the text
        |
        v
cat receives: active\n
```

`seq_file` is the kernel helper used to produce read output safely.
It handles repeated and partial userspace reads while your show callback writes
logical output with helpers such as `seq_puts`.

For this single-value status file, the callback is intentionally small:

```c
static int rk_status_show(struct seq_file *output, void *unused)
{
	seq_puts(output, "active\n");
	return 0;
}
```

Returning zero means the output was produced successfully.

## Publish and unpublish the entry

`proc_create_single` connects a name, permissions, and show callback:

```c
proc_entry = proc_create_single(
    "rklings", 0444, NULL, rk_status_show);
```

The arguments mean:

```text
"rklings"       create /proc/rklings
0444            readable by owner, group, and others; writable by nobody
NULL            place it at the root of /proc
rk_status_show  generate its contents when read
```

Store the returned `struct proc_dir_entry *` because the same component owns its
removal:

```c
proc_remove(proc_entry);
proc_entry = NULL;
```

Reject a second publication attempt while `proc_entry` is already owned.
This prevents replacing or losing the only handle needed for cleanup.

## Preserve dependency order

The proc entry and state have a dependency even though this first status
callback prints fixed text:

```text
state must exist before interfaces that expose state

init                                  exit
----                                  ----
create state                          remove proc entry
     |                                     |
     v                                     v
publish proc entry                    destroy state
```

The order prevents a reader from entering a published callback after the data
behind that interface has been freed.
Later lessons make the callback read the state directly, so establishing this
order now matters.

If publication fails, initialization must roll back the state acquired just
before it:

```text
rk_state_create() succeeds
        |
rk_proc_publish() returns -ENOMEM
        |
        +-- rk_state_destroy(state)
        +-- state = NULL
        +-- return -ENOMEM
```

Preserve the publication error while performing that cleanup.

## Implement it

In `include/rootkit.h`:

1. Add `rk_proc_publish` and `rk_proc_unpublish` declarations.
2. Mark publication `__must_check`.

In `interface/proc.c`:

1. Keep a private pointer to the published proc entry.
2. Reject publication when an entry is already owned.
3. Honor the supplied publication failure point.
4. Create `/proc/rklings` with mode `0444` and `rk_status_show`.
5. Return `-ENOMEM` if creation fails.
6. Remove the entry and clear its pointer during unpublish.

In `core/main.c`:

1. Create state first.
2. Publish the proc entry second.
3. If publication fails, destroy the state and return the same error.
4. On exit, unpublish before destroying state.

The supplied Kbuild already includes `interface/proc.o` in the module.

## Test it

After completing the implementation, build it and enter the VM:

```console
$ ./rklings run L03
```

Inside the VM:

```console
root@victim:~# insmod /rklings/rklings.ko
root@victim:~# cat /proc/rklings
active
root@victim:~# stat -c '%A %a' /proc/rklings
-r--r--r-- 444
root@victim:~# rmmod rklings
root@victim:~# cat /proc/rklings
cat: /proc/rklings: No such file or directory
```

Repeat the load and unload once.
Successful repetition proves that `proc_entry` is cleared rather than retaining
a stale pointer.

## Validate

From the repository root:

```console
$ ./rklings validate L03
```

The validator checks component ownership, mode `0444`, generated contents,
repeated publication lifetimes, exact errors at every injected failure point,
rollback after publication failure, and reverse teardown order.
